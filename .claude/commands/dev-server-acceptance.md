Launch an isolated agent-wrangler dev instance, self-test the current changes against it, and hand me back an artifact to review — don't just tell me it works, show me.

Scope: $ARGUMENTS if given, otherwise infer what to check from `git diff main...HEAD`.

1. Use the run-dev skill to launch an isolated dev instance (own data dir, port, tmux socket).
2. Dispatch one subagent to actually exercise the change against the running server. It should pick a browser-driving tool in this order: the `rodney` CLI if `command -v rodney` succeeds, else the chrome-devtools MCP, else the playwright MCP. It navigates to the relevant pages/features, exercises them, saves screenshots to files in its scratchpad dir, watches the console for errors, and returns ONLY a text manifest — file path, caption, what was checked, and pass/fail/notes per screenshot. It must never return raw image bytes/content back to you.
   Each screenshot must actually exhibit the behaviour its caption claims, not just be taken near it:
   - Before capturing, identify the specific element(s) the caption is about (via the accessibility snapshot / DOM query, not eyeballing the rendered image) and confirm each is inside the viewport and actually rendered — scroll it into view first if it isn't, and don't accept an element that's zero-size, `display:none`, or occluded by something else.
   - For anything transient (a tooltip, popover, dropdown, toast, hover state), trigger it and capture in the same tool-call sequence with no intervening navigation/mouse-move/wait that could dismiss it, then re-check with the same DOM/snapshot query that the transient element is still present at the moment of capture — a screenshot of the tooltip having already closed is a failure, not a pass.
   - If either check fails, retry once (scroll into view / re-trigger / re-hover) before giving up. If it still fails, say so plainly in the manifest per-screenshot notes (don't ship a screenshot that doesn't show what it claims and mark it pass anyway).
   The manifest's per-screenshot notes should say what was checked to confirm the relevant UI was actually visible in-frame, not just that the action was performed.
   If using the chrome-devtools MCP's `take_screenshot`, always pass an explicit `filePath` on every call — without it, only the first screenshot in the browser session actually gets written to disk, and later calls silently leave that same file on disk while returning a different image inline, so a later screenshot's manifest entry can point at an earlier, unrelated capture. After saving, re-read the file back once to confirm it shows what the entry claims before including it in the manifest.
3. As soon as the manifest comes back, tear the dev server down immediately per the run-dev skill's teardown steps (kill the server PID and its tmux socket) — the screenshots are already on disk, nothing further needs the server running.
4. Dispatch a second subagent to build the review artifact, so the manifest and screenshots never bloat your own context. Give it the manifest and screenshot paths. It should load the artifact-design skill, write an HTML report (a checklist of what was verified, plus each screenshot embedded as a base64 data URI via a Bash/node one-liner — never via the Read tool, so the images never load into its context either), and return just the resulting file path plus a suggested title, description, and favicon emoji.
   Screenshots must be viewable at full resolution, not just as a shrunk inline thumbnail: show each at a reviewable inline size, but make it clickable to open a fullscreen lightbox (image at its native resolution over a dark backdrop, dismissible via a close control, Escape, or clicking the backdrop). Implement the lightbox with plain inline CSS/JS (no external libraries) since the report is published as a self-contained Artifact.
5. Call the Artifact tool yourself on that file path to publish it for review. Do not read the manifest or screenshots into your own context at any point.
